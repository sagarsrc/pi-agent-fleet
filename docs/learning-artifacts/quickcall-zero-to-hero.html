Hour 1 — Foundations

Pretraining vs post-training

Pretraining makes the model broadly competent: giant next-token training on internet/code corpora until it learns syntax, world knowledge, and generic coding behavior.

Post-training comes after: smaller, targeted stages that make the base model useful for specific behaviors (instruction following, pairwise preference alignment, code-agent reward optimization).

QuickCall story is entirely post-training: you are not claiming a new base model, you are claiming better adaptation from real engineering workflow traces.

SFT vs DPO vs RLHF vs RLVR

MethodWhat it doesWhen to use it
SFT Supervised Fine-TuningShow the model good input→output demonstrations; push probability mass onto those tokens.Best warm start for style, repo conventions, task framing, and high-confidence accepted traces.
DPO Direct Preference OptimizationGive prompt + chosen + rejected; train it to score chosen above rejected.Best first monetization of QuickCall traces because telemetry can be denoised into pairs.
RLHF Reinforcement Learning from Human FeedbackTrain a reward model from preferences, then optimize policy with PPO while staying close to reference via KL penalty.More flexible than DPO, but heavier: reward model, rollouts, policy drift, reward hacking.
RLVR RL from Verifiable RewardsSkip the human reward model when correctness can be checked by tests, compilers, or exact answers.Powerful in code, but only when the verifier actually covers the real value.

Founder line: DPO monetizes offline preference data first; add RLHF/RLVR later.

GRPO and GSPO in one minute

  • GRPO — group-relative optimizer from the DeepSeekMath lineage; compares sampled outputs within groups instead of a separate reward model + PPO stack.
  • GSPO — Qwen’s stabler successor for larger-scale reasoning/coding RL.
  • Head-of-AI line: “GRPO/GSPO matter because once you have agent trajectories and verifiable outcomes, optimizer choice becomes a room-level technical detail, not implementation trivia.”

Worked example: QuickCall trace → preference pair

  1. Engineer asks: “Add Zod validation to settings endpoint; keep team logging style; no default export.”
  2. Model suggests patch A. Engineer accepts it.
  3. Within 8 minutes, engineer rewrites handler, swaps logger call, adds missing test, removes default export.
  4. Final patch persists; tests pass; review approves.

The DPO row:

{
  "prompt": "Add Zod validation to settings endpoint; keep team logging style; no default export.",
  "chosen": "final persisted diff after human correction",
  "rejected": "original model diff shown first",
  "metadata": {
    "pair_type": "accept_then_edit",
    "validators_pass": true,
    "review_approved": true,
    "removed_ratio_15m": 0.0
  }
}

Caveats: prefer candidate-vs-candidate rows when you have them; if chosen is longer because human had to repair pieces, DPO may learn “longer = better.” Bucket pairs by edit ratio and length delta.

Hour 1 recap

  • QuickCall is post-training, not pretraining.
  • SFT teaches style and task shape; DPO teaches preference boundary; RLVR teaches verifier-backed correctness.
  • First real asset is clean chosen/rejected or desirable/undesirable rows, not raw clicks.
  • DPO is best v1 because it directly monetizes preference traces without full RLHF complexity.
  • Technical trap: DPO can learn verbosity bias if pair construction is sloppy.

Hour 2 — Thesis

Why traces → preference pairs are the asset

Public git data mostly shows only final shipped code. It rarely shows what was shown, rejected, accepted then reverted, lightly polished, or violated local taste.

QuickCall’s asset is those missing counterfactuals and corrections.

Best founder sentence: “Our moat is not more code; it is more decision traces per unit of code.”

Candidate-trajectory schema

One canonical object per shown suggestion before materializing SFT/DPO/KTO rows.

{
  "candidate_id": "cand_456",
  "team_id": "team_123",
  "tool": "cursor|claude_code|codex|copilot|zed",
  "prompt": { "messages": [...] },
  "shown_output": "unified diff or patch",
  "accept_state": "accepted_full|accepted_partial|rejected|ignored",
  "persistence": {
    "unchanged_30s": false,
    "mostly_unchanged_300s": true,
    "removed_ratio_15m": 0.0
  },
  "validators": { "lint": "pass", "tests": "pass" },
  "review": { "approved": true },
  "session": { "success": true },
  "security": { "rights_class": "tenant_only|poolable", "pii_redacted": true }
}

A DPO row is then just prompt + chosen + rejected.

Why open code models are the vehicle

  • Give four things closed APIs do not: weight access, cheap iteration, per-team deployment flexibility, and transparent post-training recipes.
  • Qwen2.5-Coder exposes explicit SFT/DPO recipe and permissive Apache-2.0 licensing.
  • Yi-Coder gives a smaller Apache fallback.
  • vLLM keeps the on-prem story credible.
  • Translation: “QuickCall can learn on top of commoditizing open capability instead of trying to outrun frontier labs on pretraining.”

Training economics and budget tiers

Two truths can both be true: frontier RL can be very expensive, but QuickCall v1 is cheap because LoRA/QLoRA + 7B–14B + offline SFT/DPO moves cost far below frontier scale.

Position: between buckets 2 and 3 — a data/refinement layer, not a new frontier-model capex story.

Labs’ incentives — partner, not competitor

  • They want domain data (OpenAI Data Partnerships, DPO/RFT products).
  • They want code-session data specifically (Anthropic DPP explicitly invites Claude Code sessions).
  • They do not automatically own business data; both OpenAI and Anthropic say commercial data is not used for training by default.

Best framing: “You have models and training infra; we have cross-tool, opt-in, rights-clean coding preference traces you usually do not see outside your own product surface.”

Flywheel math

Illustrative: 100 developers, 2 AI-assisted sessions/day, 20 workdays/month, 1 clean pairable event every 3 sessions after filtering.

  • Sessions / month = 100 × 2 × 20 = 4,000
  • Clean pair candidates / month ≈ 1,333
  • 6 months, 1 design partner ≈ 8,000 clean pairs
  • 12 months, 3 similar partners ≈ 48,000 clean pairs

Why it matters: 48k is the same order as Zephyr’s 61k and Decode’s 53.6k. Cold-start is hard, but not absurd.

Twelve hardest questions and rebuttals

Click to expand all 12 rebuttals
  1. If Anthropic/OpenAI/GitHub want this, why won’t they do it themselves?
    They will on first-party surfaces. QuickCall matters only as a cross-tool, provider-neutral, opt-in normalization layer; rights and consent remain real bottlenecks.
  2. Why not synthetic data or teacher distillation?
    Synthetic data is great for cold start, but real human correction/revert behavior contains signal synthetics do not observe.
  3. Do you have enough data volume before patience runs out?
    First useful signal appears in tens of thousands, not millions. Real risk is usable yield after filtering, not volume alone.
  4. Aren’t accept/reject labels too noisy?
    Yes raw. Use candidate-vs-candidate when possible; otherwise require persistence, edit trajectory, undo/revert, validators, and review outcome.
  5. Why not just use RAG, prompts, and team rules?
    RAG tells the model what exists; preference traces tell the model what humans actually keep when several plausible diffs are possible.
  6. Why not rely on tests and RLVR instead of human preferences?
    Use RLVR when the verifier covers value. Many engineering preferences are weakly verifiable: taste, naming, diff size, reviewer comfort.
  7. How do you avoid DPO learning the wrong thing—especially “longer patch = better”?
    Length-controlled pairs, small β sweep, win-rate by length bucket, prefer cleaner candidate-vs-candidate rows.
  8. How will you prove gains are real, not eval gaming?
    Split by team + repo + time, decontaminate, report private and public metrics separately, then verify in shadow deployment.
  9. How do you solve privacy, IP, and licensing?
    Opt-in collection, edge redaction, secret scanning, rights classes per row, and strict tenant-only vs poolable separation.
  10. What if team conventions churn or key engineers leave?
    Use rolling windows, decay old traces, pooled base + team residual adapter, and refresh often.
  11. If open models commoditize, where is durable value?
    Rights-clean data, eval harnesses, and team calibration. As base capability commoditizes, org-specific behavior becomes more valuable.
  12. Does this become services or per-customer fine-tunes?
    Risk is real. Scalable version is hierarchical: pooled base adapter + per-team residual adapters when data volume justifies.

Open gaps

  • Raw→clean yield. Strong precedents, but exact retention after redaction, dedup, and ambiguity filters is uncertain.
  • Per-team cold-start threshold. “Tens of thousands can matter” is supported, but the exact breakpoint by language/repo type is not.
  • Objective split by task. DPO first and RLVR later is sensible, but exact routing across inline edit / refactor / bug-fix / review-comment is still thin.
  • Pooling legality in practice. Technical mitigations are clear; contract-level willingness to allow cross-company pooling remains uncertain.
  • Causal online lift durability. Strong offline harness is necessary, but not a full substitute for multi-month real-user A/B evidence.

4-line emergency recap

  1. Post-training, not pretraining.
  2. Decision traces, not code volume.
  3. Qwen2.5-Coder-14B + SFT→DPO first.
  4. Win condition = engineers accept more and edit less.
