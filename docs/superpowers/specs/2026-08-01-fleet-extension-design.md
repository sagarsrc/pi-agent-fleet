# Fleet — pi extension for DAG-of-agents with contracts and records

**Date:** 2026-08-01
**Status:** Draft, awaiting user review
**Repo:** `pi-fleet-extension` (greenfield, TypeScript pi extension)

## 1. Overview

`fleet` is a pi extension that lets the main agent (or user) define a **static DAG of worker agents**, preview it, launch it, and watch it execute — with per-worker **output contracts**, **live progress visibility**, and a machine-written **report** at completion.

v1 scope: static DAG, pi-only workers, in-process execution. The DAG is generated by the main agent from a plan (or written by the user), validated and previewed by the extension, then executed with dependency-ordered scheduling.

Explicitly deferred (v2+): JIT node-adding mid-run, iterative/looping DAGs (reviewer-gated iteration cycles), claude/codex providers, cross-session persistence (tmux/daemon mode), auto-retry.

## 2. Goals and non-goals

**Goals**
- DAG defined as data (fleet.json-compatible), previewable before launch, launch requires confirmation
- Per-worker-class output contracts, verified in code at worker exit
- Workers are DAG-aware: each worker knows the full graph (read-only), its upstream inputs, and what downstream nodes require of it (Airflow-style node contracts)
- Live per-worker progress in the TUI (tintin pi-subagents-grade visibility)
- Single-writer state: one `state.json`, no sentinel files, `.fleet/` git-ignored
- Easy kill: one worker or whole fleet, via command or UI key
- Uniform machinery: a single subagent ("fleet of one") goes through the same path as a 20-worker fleet
- Machine-written `report.md` at completion — the thin bridge to the doc skill (path-link only, no structural coupling)

**Non-goals (v1)**
- No auto-restart, no auto-recovery, no babysitting. Failures surface to the orchestrator; operator/agent decides (philosophy inherited from dag-fleet skill)
- No mid-run steering of workers (tintin does this; fleet v1 defers — kill + edit + relaunch)
- No multi-provider (claude/codex) support
- No git worktree isolation
- No persistence beyond the pi session

│  │ DAG core (pure TS, testable)     │                │   │
│  │  - parse/validate fleet.json     │                │   │
│  │  - topo sort, cycle detect       │                │   │
│  │  - ready-queue scheduler         │                │   │

│  │  - event subscribe → state + UI  │                │   │

### Execution model: in-process `createAgentSession`

Each worker runs as an independent `AgentSession` inside the pi process (tintin pi-subagents pattern), with its own model, tools, system prompt, and conversation context.

**Why not tmux:** the bash fleet skills used tmux because they execute from shell, outside pi. Inside an extension, tmux adds a layer while providing nothing the event stream doesn't.
**Why not `pi -p` subprocess:** process isolation is the only gain; streaming requires JSONL parsing, kill requires signals, cost tracking requires post-hoc parsing. In-process gives all of these natively.
**Accepted tradeoff:** fleet lifetime = pi session lifetime. Worker `session.jsonl` files persist on disk, so a future `--resume`-style recovery is possible, but v1 does not implement it.

Kill = `AbortController.abort()` per worker; fleet kill = abort all. Easy, immediate, no orphan processes.

## 5. Fleet definition (fleet.json-compatible)

Fleet root: `.fleet/<short-name>-<timestamp>/` under the project cwd. Short names (kebab-case, ≤ 4 words). Extension auto-creates `.fleet/.gitignore` containing `*` on first use — no sentinel/state files ever enter git.

```json
{
  "fleet_name": "auth-research",
  "type": "dag",
  "config": {
    "max_concurrent": 4,
    "model": "k2p6",
    "warn_cost_usd": 5.0
  },
  "workers": [
    {
      "id": "research-auth",
      "type": "research",
      "task": "Research OAuth2 patterns for this codebase",
      "depends_on": [],
      "outputs": [
        { "path": "output/findings.md", "kind": "markdown", "required": true }
      ]
    },
    {
      "id": "build-auth",
      "type": "code-run",
      "task": "Implement login flow",
      "depends_on": ["research-auth"],
      "outputs": [
        { "path": "src/auth/login.ts", "kind": "file-exists", "required": true },
        { "path": "output/notes.md", "kind": "markdown", "required": false }
      ]
    },
    {
      "id": "review-auth",
      "type": "reviewer",
      "task": "Review the auth implementation",
      "depends_on": ["build-auth"],
      "outputs": [
        { "path": "output/review.md", "kind": "verdict", "required": true }
      ]
    }
  ]
}
```

Schema stays a superset of the dag-fleet skill's schema (same field names and semantics), so existing mental models, docs, and tooling (`dag-viz.py` etc.) transfer.

## 6. Contract system

### Output kinds

Declared per worker in `outputs[]`. Verified **at worker exit** (fail fast), before dependents are released.

| kind | check | typical class |
|---|---|---|
| `markdown` | file exists, non-empty, starts with `#` | research |
| `file-exists` | file exists, non-empty (repo-relative paths allowed — code edits) | dev |
| `verdict` | file exists + matches `^verdict:\s*(lgtm|iterate|escalate)` AND has a non-empty body below the verdict line | reviewer |

The `verdict` file IS the review (ported from iterative-fleet): verdict line first, then actionable per-worker fix instructions — file path, function name, what to change. A verdict-only file with no body fails the check.
| `json` | file exists + parses | data producers |
| `yaml` | file exists + parses | data producers |

`required: true` failing → worker marked `contract_failed` in state, dependents stay blocked, orchestrator agent is notified with the failed checks. No auto-retry.
`required: false` missing → warning in state + report only.
No `outputs` declared → worker is done on natural completion (backward compatible).

### DAG-aware workers (Airflow-style node contracts)

The DAG is a **shared, readable object**. Every worker's generated prompt includes:

1. **Full DAG view** — ASCII rendering + each node's id, type, task, and declared outputs (read-only knowledge)
2. **Own node** — id, task, its own output obligations
3. **Upstream inputs** — resolved absolute paths to every completed dependency's declared outputs
4. **Downstream requirements** — list of dependent nodes and which of *this* node's outputs they will consume (derived from dependents' declared outputs + task text)

This solves the "research agent didn't write `output.md`, everything downstream fails" problem at the source: the worker knows exactly what it must produce and *for whom*, before it starts.

### Per-node write scoping

Workers can read the entire DAG state but mutate only their own node. Mechanism: worker sessions are created with the fleet extension loaded in **worker mode** (scoped by `FLEET_WORKER_ID`), registering two tools:

- `fleet_dag_read` — returns current state.json content (any node)
- `fleet_node_update` — writes to the caller's own node only: `status_note`, `progress`, `produced_outputs`. Attempts to touch other nodes are rejected by the tool.

The extension core remains the only writer of lifecycle fields (`status`, `started_at`, `ended_at`, `contract_result`).

## 7. State management

Single file: `.fleet/<fleet>/state.json`. Atomic writes (write-temp-then-rename). No `.done` sentinels, no per-worker `status.json` files, no lock files in git (`.fleet/` is git-ignored wholesale).

```json
{
  "fleet_name": "auth-research",
  "status": "running",
  "created_at": "...",
  "cost_usd_estimate": 0.42,
  "nodes": {
    "research-auth": {
      "status": "completed",
      "started_at": "...", "ended_at": "...",
      "turns": 12, "tokens": 48200, "cost_usd_estimate": 0.11,
      "contract_result": { "ok": true, "checks": [...] },
      "produced_outputs": ["output/findings.md"],
      "status_note": "found 3 relevant patterns"
    }
  }
}
```

Per-worker artifacts that remain files (legitimately): `workers/<id>/prompt.md`, `workers/<id>/session.jsonl` (full trace), `workers/<id>/output/*`. All inside git-ignored `.fleet/`.

## 8. Scheduling

- Kahn's layered topo-sort at validation time; cycles rejected before anything spawns (`CYCLE:a,b,c` error)
- Ready-queue: node dispatched when all `depends_on` nodes reach `completed` (contract-passed)
- Concurrency: ≤ `config.max_concurrent` active sessions; queue per tintin pattern
- `contract_failed` / `failed` / `killed` node → dependents permanently blocked (`blocked` status), orchestrator notified; rest of DAG continues
- Fleet completes when every node is terminal (`completed|failed|contract_failed|killed|blocked`) → `report.md` written, orchestrator notified

## 9. Tool and command surface

**LLM tools (registered on extension):**

| tool | purpose |
|---|---|
| `fleet_plan` | accept fleet definition (inline JSON), validate schema + cycles + contracts, write fleet root, return ASCII preview. Does NOT launch |
| `fleet_launch` | launch a planned fleet (requires prior `fleet_plan`; in TUI mode requires user confirmation of the preview) |
| `fleet_status` | current state: per-node status, turns, tokens, cost |
| `fleet_report` | generate/return report.md on demand |
| `fleet_kill` | kill one worker or entire fleet |

**User commands:**

| command | purpose |
|---|---|
| `/fleet viz` | ASCII DAG of active/last fleet (widget or dag.md fallback) |
| `/fleet status` | live status table |
| `/fleet kill <id\|all>` | kill worker or fleet |

Fleet-of-one: the main agent using a single subagent calls `fleet_plan` with one worker — identical machinery, records, contract checks, report.

## 10. UI

### DAG preview (pre-launch gate)

`fleet_plan` renders ASCII DAG (TS port of `lib/dag-viz.py` — layered layout, dependency arrows). Shown via `ctx.ui` widget + included in tool result so the LLM can present it. In TUI mode, `fleet_launch` triggers a confirm dialog showing the preview; no silent launches.

Graphs too wide/tall for the terminal (> ~15 nodes or > terminal width after layout) → extension writes `.fleet/<fleet>/dag.md` (mermaid + ASCII) and the widget shows a summary + path.

### Live run widget

Above-editor widget (tintin-grade), one line per node:

```
● fleet: auth-research  (2/3 done · $0.42)
├─ ✓ research-auth · 12 turns · 48.2k tok · $0.11
├─ ⠹ build-auth · 7 turns · 21.0k tok · editing src/auth/login.ts…
└─ ○ review-auth · waiting on build-auth
```

Updated from session events (tool calls, token usage, turn boundaries). `dag.md` fallback for large fleets.

## 11. Report (doc-skill bridge)

On fleet completion (and on demand via `fleet_report`), extension writes `.fleet/<fleet>/report.md`:

- DAG summary (ASCII + node table)
- Per-worker: status, turns, tokens, cost estimate, contract check results, produced outputs, `git diff --stat` for code workers (captured at completion — makes code-agent work visible without reading code)
- Totals + duration
- Optional `experiment: "NNN"` tag in fleet.json is echoed into the report header — informational only

Doc skill integration = **path link only**. The agent/user references the report from a checkpoint or finding (`see .fleet/auth-research-.../report.md`). Fleet never reads doc skill internals; doc skill never parses fleet state.

## 12. Cost tracking

Pi exposes token usage per session; extension maintains a running cost estimate per worker and fleet total using model pricing from the model registry. `config.warn_cost_usd` exceeded → warning to orchestrator + widget indicator. No hard caps in v1 (pi has no `--max-budget-usd` equivalent for in-process sessions; warning-only was the explicit choice).

## 13. Error handling

| failure | behavior |
|---|---|
| validation error (schema, cycle) | `fleet_plan` fails, nothing written except error detail |
| worker session error/crash | node → `failed`, dependents → `blocked`, orchestrator notified, DAG continues |
| contract check fail | node → `contract_failed`, same propagation |
| kill worker | node → `killed`, dependents → `blocked` |
| kill fleet | abort all controllers, non-started nodes → `killed`, state + report written |
| pi session exit | in-memory runtime lost; `state.json` + `session.jsonl` files remain on disk (recovery is v2) |

## 14. Testing

- DAG core (parse, topo sort, cycle detection, ready-queue, contract verifiers, state read/write) is pure TypeScript — unit tested with vitest, no pi runtime needed
- Contract verifiers tested against fixture files (valid/invalid markdown, verdict, json)
- Scheduler tested with fake worker-runtime (injected interface) — deterministically simulates completion/failure ordering
- UI/widget: manual verification via `pi -e ./src/index.ts`
- One end-to-end smoke fleet: 2 workers (research → write), real models, tiny tasks, validates contracts + report generation
